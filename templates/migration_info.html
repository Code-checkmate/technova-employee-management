AWS Database Migration Architecture

Enterprise roadmap and operational blueprint for migrating TechNova Employee Management System from Amazon RDS for MySQL to Amazon Aurora MySQL.

Production Playbook

Architecture Before Migration

Baseline

Application server running on Amazon EC2 connects directly to a single-instance Amazon RDS for MySQL database.

Client Web Browser
EC2 Application Server (Flask / Gunicorn)
Amazon RDS for MySQL 8.x
Host: technova-db.c9akxxxxxx.rds.amazonaws.com

Architecture After Cutover

Target

EC2 Application Server connects to high-availability Amazon Aurora MySQL cluster with distributed storage and read replicas.

Client Web Browser
EC2 Application Server (Flask / Gunicorn)
Amazon Aurora MySQL Cluster
Cluster Endpoint: technova-aurora.cluster-c9akxxxxxx.rds.amazonaws.com

Critical Engineering Distinction: Migration vs Cutover

Changing an environment variable (MYSQL_HOST) only changes the target network endpoint; it DOES NOT migrate data. A complete database migration requires synchronizing database schema, indexes, and existing employee rows from Amazon RDS to Amazon Aurora before updating application configuration.

7-Phase Migration Implementation Plan

The TechNova application operates normally against the source Amazon RDS for MySQL instance. Establish baseline performance metrics:

  • Query latency and transactions per second (TPS).
  • Total table counts and row count snapshot: SELECT COUNT(*) FROM employees;
  • Verify backup retention and Amazon RDS automated snapshot status.

Deploy target Aurora cluster within the same Amazon VPC or peered VPC:

  • Create an Aurora MySQL 8.0-compatible DB cluster with 1 primary writer and at least 1 reader instance in a multi-AZ configuration.
  • Apply custom DB parameter group matching RDS MySQL character set and collation (utf8mb4).
  • Configure Security Groups allowing inbound traffic on port 3306 exclusively from the EC2 Application Server security group.

Choose an appropriate AWS migration mechanism based on downtime tolerance:

Option A: Aurora Read Replica (Recommended for Low Downtime)

Create an Amazon Aurora Read Replica directly from the RDS MySQL DB instance. AWS automatically replicates data using binary logs. Once replica lag reaches 0, promote the replica into a standalone Aurora cluster.

Option B: AWS DMS or Snapshot Migration

Use AWS Database Migration Service (DMS) with Ongoing Replication (CDC) or restore an Amazon RDS snapshot directly to an Aurora MySQL DB cluster.

Validate that all employee data on the Aurora destination strictly mirrors the source RDS instance:

  • Compare total rows: SELECT COUNT(*) FROM employees on RDS vs Aurora.
  • Verify table schema, constraints, primary key auto-increment values, and indexes (ix_emp_dept_status).
  • Execute checksum verification or compare MD5 hashes of sample employee subsets.

Execute the cutover by updating application environment configuration:

  • Stop background writes or place source RDS in read-only mode during cutover maintenance window.
  • Update MYSQL_HOST to the Aurora Cluster Endpoint (e.g., technova-aurora.cluster-xxxx.us-east-1.rds.amazonaws.com).
  • Restart application service (e.g. sudo systemctl restart technova-ems).

Conduct end-to-end verification through application test client and browser:

  • Verify /health returns HTTP 200 with active Aurora connection.
  • Test Employee CRUD: Create test employee, view in directory, edit fields, and delete test record.
  • Monitor Amazon CloudWatch metrics: CPU utilization, active connections, and Aurora Replica Lag.

Preserve business continuity contingency:

  • Keep the original Amazon RDS for MySQL instance in standby for the agreed contingency duration (e.g., 48 to 72 hours).
  • If unexpected regression occurs, rollback by reverting MYSQL_HOST to RDS MySQL endpoint and restarting application service.
  • Once acceptance sign-off is granted, decommission source RDS instance after taking a final manual DB snapshot.

Data Migration Verification Checklist

Verification Check Procedure / Command Expected Result Status
1. Row Count Parity SELECT COUNT(*) FROM employees; RDS count == Aurora count Required
2. Unique Email Integrity SELECT email, COUNT(*) FROM employees GROUP BY email HAVING COUNT(*) > 1; 0 duplicate rows Required
3. Department Distribution SELECT department, COUNT(*) FROM employees GROUP BY department; Identical departmental counts Required
4. Auto-Increment State SELECT AUTO_INCREMENT FROM information_schema.TABLES WHERE TABLE_NAME='employees'; Aurora counter >= max(id) Required
5. Application Health Check curl -f http://ec2-instance:5000/health HTTP 200 OK, latency < 50ms Required
6. Write Capability (CRUD) Create and delete a verification test employee record Successful write and commit Required
